## 1. 规划原则、决策驱动和路线选择

### 1.1 原则

1. P0 优先：先得到真实、可运行、可验证的单路径系统，再扩第二算法或炫技功能。
2. 证据优先：每个“完成”都要有代码、测试、运行记录、数据或材料链接，不能只报口头进度。
3. 技术诚实：mock、人工结果和真实算法严格区分；未验证指标不写成已达标。
4. 提前冻结：9 月前完成 P0，9 月主要用于验证、材料、演练和提交。
5. 单点负责：每项任务只能有一个最终负责角色；“大家一起做”等于无人负责。

### 1.2 三个最高决策驱动

1. 是否能在 8 月上旬拿到有合法来源和稳定真值的可评估数据；
2. 是否能在 8 月中下旬由真实算法产生接近或达到 85%/90% 的结果；
3. 是否能在 8 月底前形成前端、后端、算法、复核、报告、证据包的一条完整链路。

### 1.3 可选路线

| 路线 | 优点 | 主要代价/风险 | 本计划态度 |
|---|---|---|---|
| A. 隐蔽工程影像结构化验真单主线 | 与“视频输入 + 结构化报告 + 哈希存证”概念贴合；后端闭环清晰 | 90% 阈值高；公开数据没有完整尺寸真值；还依赖标定、控制点和独立测量 | 当前证据评分 48/100，保留受限预研；只有取得尺度/测量真值后才重评 |
| B. PPE/违章识别单主线 | Construction-PPE 可快速形成 person/helmet 基线；85% 阈值相对低 | 没有一个公开集覆盖通信施工视频与完整 PPE 负类；下载审计还发现跨 split 近重复和域外样本 | 当前证据评分 72/100，暂定推荐；须通过两日门禁和团队签署 |
| C. 两条主线同时正式实现 | 展示完整、理论上得分面广 | 当前只有两名已确认开发角色，算法人员未定，极易两条都不达标 | P0 禁止；只有主线全部绿色后才允许作为 P1 |
| D. 只做平台和 mock，不做真实算法 | 可较快形成漂亮演示 | 不满足赛题量化验证，不能构成最终可信提交 | 仅作 7 月集成过渡，不能作为最终路线 |

### 1.4 决策记录

- 决策：截至 2026-07-19，只选择一个正式算法主线；先用 mock 打通工程链路，但最终 submission 必须绑定非 mock 算法和冻结评估运行。
- 选择依据：截止日期、当前人员确定度、指标硬约束、材料要求。
- 强反方观点：先把两个算法都做出 UI，后续哪个数据好用哪个，可以增加灵活性。
- 反驳：双线会重复消耗标签定义、数据清洗、评估、接口和材料时间；在算法负责人尚未确认时，灵活性实际上会转化为长期不做决策。
- 保留余地：7 月 19 日前允许 A/B 并行做轻量数据可行性调查，不允许并行建设两套正式产品功能。
- 后续动作：项目统筹人和算法/数据负责人根据“数据来源、真值成本、基线结果、许可证”形成一页决策记录并签字/确认。

详细证据、评分、标签与门禁见 `docs/algorithm-data/`；development runner 合同见 `docs/DEVELOPMENT_EVALUATION_RUNNER.md`，本机算力与待批准 pilot 见 `docs/algorithm-data/PPE_BASELINE_COMPUTE_PLAN_2026-07-10.md`。公开数据只用于预训练/基线；正式指标必须使用授权通信施工视频、按视频/现场/工程实体隔离的 QA 盲测集。

## 2. 优先级定义

### 2.1 P0 - 不完成就没有完整参赛作品

- 报名审核状态、团队名单、主体和指导教师信息确认；
- 明确唯一指标主线和官方口径；
- 确认算法/数据负责人、数据来源、许可证/授权和标签规范；
- 真实项目/工点/设计基线或版本化 JSON/CSV 工程基线；
- 真实视频/图片上传、SHA-256、元数据和对象存储；
- 异步分析任务、失败/重试、版本化算法 adapter；
- 显式 mock adapter，仅用于开发演示；
- 至少一个真实非 mock 算法 adapter；
- 结构化结果、证据帧、工程对象关联、人工复核和版本记录；
- 进度快照或所选指标路径对应的工程化结果；
- 结构化报告；
- manifest、文件摘要、审计哈希链、独立篡改校验；
- 前端完整接入真实 API，不保留假成功主路径；
- 冻结数据集、评估口径、样本级结果和真实指标；
- 一套可重复部署和演示的系统；
- 五类比赛材料及报名表/提交检查。

### 2.2 P1 - P0 全绿后增加得分

- 第二感知来源或可演示的传感器/IoT 数据适配；
- 更自动化的工程对象对齐；
- 第二算法任务的真实 baseline；
- Ed25519 服务端签名；
- 更丰富的进度看板、筛选、导出和对比视图；
- 模型对比、消融实验和更多失败案例分析；
- 更稳定的 Docker/离线部署包；
- 演示可用的准实时进度更新，但不得冒充直播流。

### 2.3 P2 - 本轮默认不做

- RTSP/WebRTC 多路直播；
- 真实 IoT 硬件和大规模传感器接入；
- QGIS/CAD 全量几何解析与自动空间配准；
- 联盟链、公链或外部司法存证；
- 3D 数字孪生、元宇宙场景；
- 多租户、企业 SSO、复杂权限中心；
- 移动 App；
- 大规模 GPU 集群调度。

规则：P0 任一关键门禁为红色时，不批准 P1；P2 只有项目统筹明确更改范围后才进入计划。

### 3.3 工作节奏

- 每周一：30 分钟计划会，确认本周 3 个以内团队级结果；具体时间由团队确认。
- 每周三：固定集成检查，前端调用真实后端环境，不用静态 JSON 代替。
- 每周五：可运行 Demo + 风险审查，只展示已经落地的功能。
- 日常：每名负责人异步更新“完成/下一步/阻塞/证据链接”。

- 冻结后只接受 P0 缺陷、安全问题、数据/指标真实性问题和提交阻塞问题。

任务板每项至少包含：WBS、优先级、单一 R、单一 A、依赖、截止、验收标准、状态和证据链接。状态只允许 `Not Started/In Progress/Blocked/In Review/Done`，不用没有证据的“完成 80%”。周看板颜色定义：

- 绿：当周门禁已有运行或材料证据；
- 黄：有 owner 和恢复日期，但可能影响后续门禁；
- 红：无 owner、关键依赖未知、门禁已过期或指标/真实性不成立。

## 11. 预演失败场景

### 场景 1：8 月中旬系统很好看，但仍没有真实算法

- 早期信号：算法负责人空缺；数据讨论只有链接，没有许可证、标签和 split；每周 Demo 只用 fixture。
- 结果：9 月无法生成可信 85%/90%，验证报告为空。
- 预防：7 月 15 日人员门禁、8 月 9 日真实 baseline 门禁；未通过立即标红，不允许用 mock 关闭任务。

### 场景 2：算法报告高准确率，但测试集泄漏或口径被改

- 早期信号：相邻视频帧随机分到训练和测试；只报总体 accuracy；失败样本没有保留；每次评估分母变化。
- 结果：数字不可核查，答辩时被质疑甚至失去可信度。
- 预防：按视频/工程实体划分；metric spec 版本化；样本级结果和 split digest；QA 独立复算。

### 场景 3：9 月 10 日功能还在变化，材料、视频和系统互相矛盾

- 早期信号：8 月 28 日后仍合入 P1；截图数字手工填写；报告引用旧模型；README 未在新环境跑过。
- 结果：演示失败、材料不一致或提交包不可运行。
- 预防：分层冻结、09-01 code freeze、09-03 metric freeze、09-05 data freeze、09-09 独立复现、09-12 提前提交。
