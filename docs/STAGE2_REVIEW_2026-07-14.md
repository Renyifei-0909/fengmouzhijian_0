# 第二阶段项目评审与优先级建议（2026-07-14）

## 1. 评审结论

第二阶段的目标不应定义为“继续增加功能”，而应定义为：把第一阶段已经跑通的诚实工程闭环，升级为一条可由真实数据、真实非 mock 算法、通信工程语义和可回溯评测材料共同支撑的参赛主链。

建议正式主线暂定为：

> 视频/图片与设计基线输入 -> PPE/违章事件分析 -> 工点、工序和设计对象关联 -> 低置信度人工复核 -> 进度/偏差结论 -> 结构化报告 -> 完整性证据包 -> 冻结数据集评测。

选择 PPE/违章路线是基于当前项目材料中的可行性评分（72/100）和较低的官方门槛（准确率不低于 85%），不是因为该路线已经达到指标。隐蔽工程路线与“验真交付”叙事更贴合，但当前缺少尺度、测量真值和可合法使用的完整数据，现阶段不应同时建设为第二条正式算法主线。

当前最大的项目风险不是后端功能数量，也不是前端视觉效果，而是：算法/数据负责人、授权通信施工数据、正式路线签署和可核查指标仍未落地。若这些问题不解决，继续增加大屏、GIS、IoT 或“区块链”页面不会形成实质答辩增益。

## 3. 赛题与答辩价值判断

官方评分权重为创新性 30 分、产业应用价值 30 分、系统性 40 分。当前项目的优势主要在系统性：输入、任务、人工复核、报告、证据包和篡改检测已经形成闭环。短板集中在产业实效和真实验证：没有真实目标算法、没有授权冻结测试集，也没有达到 85%/90% 的正式证据。

| 能力 | 当前事实 | 答辩价值 | 评审意见 |
|---|---|---:|---|
| 项目、设计基线、媒体输入、任务、复核、报告 | 已有真实后端闭环 | 高 | 保持稳定，围绕真实算法补齐工程语义，不再重写 |
| 哈希、Merkle、追加式本地审计和离线校验 | 已实现本地完整性能力 | 中高 | 演示“修改任一文件后失败”；只称篡改可检测 |
| Ed25519 controlled-local evidence verifier | 已实现非正式受控本地验签 | 中 | 可证明固定制品与指定密钥关系；不称正式存证、可信时间或区块链 |
| 施工进度 | 当前是“批准基线数/基线总数”的代理指标 | 中低 | 必须改成基于工序/里程碑事件的明确定义，否则不能称实时施工进度 |
| 多源感知 | 有视频/图片、设计基线和传感器事件 API | 中 | 至少提供一个真实或经说明的第二来源样例，并解释融合关系 |
| 工程模型动态对齐 | 当前为任务显式绑定基线和字段差异 | 中 | 可称“版本化工程基线关联”，不能称自动 QGIS/CAD 空间配准 |
| PPE/违章真实算法 | 未实现 | 极高 | 第二阶段首要缺口；必须进入真实 E2E 和冻结评测链 |
| 隐蔽工程精确量测 | 未实现 | 潜在高、当前风险高 | 无标定、标尺和独立测量真值时不得输出工程级精确埋深/间距 |
| 原 Demo 其他驾驶舱/GIS/模型页面 | 多数仍为 static/mock | 低至中 | 必须显著标记原型或隔离；不能与真实工作流混为一体 |

答辩中最有价值的创新叙事不是“用了某个检测模型”或“用了哈希”，而是三者组合：

1. 视觉事件被绑定到项目、工点、工序和设计版本，而不是停留在通用安防标签；
2. 低置信度或无法对齐的结果进入人工复核，原始预测和修订均保留；
3. 原始输入、模型版本、结构化结果、复核记录和报告被同一证据清单绑定，可独立验证篡改。

该组合只有在真实非 mock 算法和样本级验证材料落地后，才可以作为产业应用创新进行陈述。

## 4. 已实现、可演示和未实现边界

### 4.1 已实现并可继续作为主链基础

- FastAPI + SQLite 的本地原型；
- 项目、工点语义设计基线和服务端摘要；
- 视频/图片上传、类型检查、视频容器探测和 SHA-256；
- 原始证据按角色鉴权回看、完整 SHA-256 先验验证、同 fd 发送和严格单 Range；
- 持久化任务、单进程启动恢复、原子领取和失败状态；
- `stub`、`demo_fixture`、默认关闭的 `remote_http` 适配合同；
- operator/reviewer/auditor 最小职责分离；
- 人工批准或驳回、JSON/HTML 报告；
- 包含原件、基线、传感器事件、分析、复核和报告的证据 ZIP；
- SHA-256、Merkle Root、本地追加哈希链和独立校验；
- Evaluation v0、development runner、unsigned evidence、本地一次性 registry 和受控本地 Ed25519 验签；
- `/backend-workflow` 的真实 API 联调流程、项目详情中的服务端证据预览，以及 `/alarms` 的 Finding 分诊、整改 Attempt、原项目/基线复验和 proof 关闭。

### 4.2 当前可以演示，但必须带边界标签

- `demo_fixture`：只用于演示软件链路，始终是 `evidence_grade=false`；
- demo Finding/整改：可演示人工分诊和证据关闭，但固定 `scope=demo`，不能算运营告警、现场事实或模型指标；
- 项目进度：只可称 MVP 代理指标，不能称实际施工实时进度；
- 设计对齐：只可称版本化基线绑定与字段比对，不能称自动空间配准；
- 传感器事件：可演示数据融合接口，但若是人工录入或样例数据，必须标注来源；
- 本地签名和哈希链：可演示制品完整性和签名关系，不能称公链、联盟链、司法存证或可信时间戳；
- 原 Demo 页面：总览、项目、报告、溯源、闭环、告警整改已接真实 API；设备、数据分析、GIS、模型服务等其余页面继续逐页标记 `static prototype`。
- 前端 Blob 原件回看：只适合本地小样例；生产大视频应改为短期播放票据或等价受控流式授权。

### 4.3 尚未实现或尚未形成正式证据

- 真实 PPE/违章或隐蔽工程模型；
- 授权通信施工视频、冻结标签和独立盲测数据；
- 官方 85%/90% 指标的合格 EvaluationRun；
- 自动 QGIS/CAD 几何配准；
- 基于实际工序事件和时间口径的实时进度跟踪；
- 生产级独立 worker、租约/心跳、多副本队列和对象存储；
- 用户/项目级身份与 RBAC；
- 可信评测 broker、隔离执行、QA 私钥托管和可信时间；
- 正式区块链或第三方存证；
- 参赛版技术方案、验证报告、对比实验原始支撑和最终演示视频。

## 5. 第二阶段优先级

### 5.1 P0 - 不完成就不能形成可信参赛主线

| 顺序 | 工作项 | 验收标准 | 主要答辩价值 |
|---:|---|---|---|
| 1 | 确认报名状态、团队名单、单一项目统筹、算法/数据、QA、材料和赛事联络责任人 | 每项有单一负责人、截止时间和书面接受；报名审核截图归档 | 避免作品完成但资格、材料或指标无人负责 |
| 2 | 向组委会书面确认“或”、多源、实时、数据支持、准确率口径和试点证明 | 问题原文、发送时间、回复原文和决定记录入库 | 降低最终验收口径反转风险 |
| 3 | 冻结 PPE/违章为唯一正式主线，或用新证据否决它 | 一页 ADR，含数据许可、真值成本、样本单元、指标和反方意见；最迟 07-19 | 防止双线消耗并保证算法工作可开始 |
| 4 | 建立合法的数据集 v0 和标签/划分清单 | 每个来源有许可证/授权、数据卡、脱敏状态；按视频/现场/人员等 lineage 隔离，保存 manifest 摘要 | 指标真实、可复现、无相邻帧泄漏 |
| 5 | 接入第一个真实非 mock baseline adapter | 对至少一段授权或合法样例视频产生真实预测；保存模型、权重、代码、配置和输入摘要；结果进入现有复核、报告、证据包 | 从软件 Demo 跨越到真实算法系统 |
| 6 | 将检测事件变成通信工程事件 | 每条事件至少有项目、工点、工序/里程碑、时间范围、类别、置信度、证据帧引用、设计版本和对齐状态；无法判断可显式表达 | 避免退化为普通安全帽检测网站 |
| 7 | 完成真实算法 E2E 和失败链路 | 上传 -> 任务 -> 真实预测 -> 低置信复核 -> 报告 -> 证据包 -> 独立校验；模型故障、低置信、无法对齐和重试均有测试 | 直接支撑系统成熟度和现场演示 |
| 8 | 冻结指标口径并完成可回溯开发评测 | 样本单元、类别、TP/FP/TN/FN、accuracy、P/R/F1、Wilson 区间写入版本化 spec；汇总可回到单样本真值与预测 | 为 85% 门槛和验证报告提供可信基础 |
| 9 | 建立 gate/final holdout 管理与 QA 执行制度 | 算法开发只看 train/validation；QA 保管 gate/final；最终运行不重试、不调参；本地工具的非正式边界保留 | 防止测试集泄漏和手填指标 |
| 10 | 统一真实前端主故事线 | 5-8 分钟内完成项目、输入、分析、证据帧、工程关联、复核、报告和篡改失败；每个数据来源和算法模式可见 | 系统性 40 分的直接展示载体 |
| 11 | 形成参赛材料的自动证据入口 | 候选版本自动导出环境、代码/模型/数据摘要、样本结果、混淆矩阵、测试结果和限制；材料不手填不存在的指标 | 避免系统与报告数值不一致 |
| 12 | 全新环境复现和候选版本回归 | 非开发者按文档启动；后端、前端、E2E、负路径和证据篡改测试通过；保存日志和版本摘要 | 系统成熟度与提交可靠性 |

P0 的关键顺序是“责任/口径 -> 数据 -> 真实 baseline -> 工程语义 -> 真实 E2E -> 评测证据 -> 演示和材料”。生产基础设施优化不能反向阻塞这一顺序。

### 5.2 P1 - P0 主链连续可演示后增加得分

- 将传感器事件或工程台账做成一个有来源说明的第二真实/半真实输入，并展示其如何改变事件判断；
- 进度视图从“批准基线比例”升级为按工序/里程碑事件计算，并明确延迟口径；
- 增加证据帧时间轴、结果筛选、事件到设计对象的可视关联和失败案例看板；
- 生成可打印 PDF 报告、核验证书和更清晰的证据包成员视图；
- Docker 冷启动、独立 worker、租约/心跳和更可靠的离线演示包；
- 在有真实样本和统一口径后做基线对比、消融和错误案例分析；
- 如组委会确认需要，评估第三方时间戳或外部存证服务，但必须保留独立哈希校验。

P1 不是指“可以晚点做的 P0”。若没有真实算法 E2E 和合法评测数据，以上任何一项都不应替代 P0。

### 5.3 P2 - 本阶段默认不投入

- RTSP/WebRTC 多路直播；
- 大规模 IoT 硬件采购和接入；
- QGIS/CAD 全量几何解析与自动空间配准；
- 3D 数字孪生、元宇宙场景；
- 公链、联盟链或司法存证平台；
- 大模型智能体编排、模型 OTA 和边缘盒子集群；
- 多租户、企业 SSO、复杂权限中心；
- 第二条正式算法主线；
- 为视觉效果重写已经稳定的后端闭环。

P2 只有在 P0 关键门禁全绿、项目统筹书面改变范围且不影响材料冻结时才可进入计划。

## 6. 阶段门禁与停止条件

### Gate A - 路线可执行（建议 07-19）

- 团队角色和暑期可用时间已确认；
- 唯一算法主线已签署；
- 数据来源、许可和标签口径有负责人；
- 组委会歧义已发出书面询问。

若失败：继续稳定平台可以，但不得宣称“算法阶段已启动”或安排第二主线。

### Gate B - 真实 baseline 可运行（建议最迟 08-09）

- 非 mock 模型可对合法样例运行；
- 模型/代码/配置/输入摘要被记录；
- 结构化输出通过严格 adapter 合同；
- 失败和低置信路径可复现。

若失败：项目进入红色风险；暂停 GIS、动画、区块链等增强项，集中解决数据与模型。

### Gate C - 真实端到端 Alpha（建议 08-12）

- 一段真实或授权样例视频完整进入复核、报告和证据包；
- 前端可看到证据帧、工程对象和算法来源；
- `demo_fixture` 与真实模型视觉上明确区分；
- 端到端测试及负路径有保存证据。

### Gate D - 首次指标风险门禁（建议 08-23）

- 固定 gate holdout 由 QA 执行；
- 指标能下钻到单样本；
- 数据泄漏检查、类别分布和失败案例齐全；
- 如未达到 85%，提交真实差距和资源决策，不允许修改页面数字掩盖差距。

### Gate E - P0 与材料冻结（建议 08-28 至 09-05）

- P0 功能冻结，真实 E2E 可连续演示；
- 最终模型、代码、数据和指标按计划分层冻结；
- 验证报告中的所有数值由冻结制品生成；
- 全新环境复现和篡改失败演示通过。

## 7. 代理职责和交付接口

多 agent 可以加快开发，但不能替代团队对数据许可、算法路线、正式指标和提交材料的人工签署。建议职责如下：

| Agent | 负责 | 必交证据 | 不得越权 |
|---|---|---|---|
| 项目评审与规划 | 需求追踪、优先级、门禁、风险和真实性审查 | 更新后的计划、风险表、决策记录、每周门禁结论 | 不把建议写成团队已接受决定 |
| 后端 | 领域模型、API、任务、算法合同、报告、证据包、部署 | 契约制品、迁移、测试、运行记录 | 不替算法负责人声称模型指标 |
| 前端 | 真实主流程、状态表达、证据帧/复核/报告交互、演示稳定性 | 页面状态清单、构建、浏览器 E2E、截图 | 不用 mock 数字替代 API 结果 |
| 算法与数据 | 数据许可、标签、模型、推理、样本级预测和错误分析 | 数据卡、manifest、模型卡、配置、预测、实验记录 | 不接触 final 私有真值后继续调参 |
| QA/评测 | 契约、回归、负路径、盲测、指标复算和复现 | 原始日志、测试报告、样本级评测、缺陷单 | 不替失败运行生成“修正后”结果 |
| Code Review | 安全、并发、数据完整性、契约和可维护性审查 | 带优先级的可复现问题和复验结果 | 不因个人风格大范围重写稳定代码 |
| 材料与答辩评审 | 技术方案、验证报告、演示脚本和问答一致性 | 每项主张到制品的证据链接、禁用表述清单 | 不写未验证的性能、产业效果或存证等级 |

共享工作区并行开发时，所有 agent 在修改前必须查看当前 diff，避免覆盖他人改动；跨模块 schema 变更应由后端、前端、算法和 QA 共同评审后再冻结。

| 无授权通信施工视频 | 红 | 07-24 仍只有公开域外 PPE 数据 | 公开数据仅做 baseline；并行争取校内/企业匿名化样例和书面授权 |
| 双算法主线并行 | 高 | 07-19 后仍未签署唯一路线 | 禁止第二主线进入正式开发 |
| 通用 PPE 检测与通信工程脱节 | 高 | 输出只有人/安全帽标签 | 强制绑定工点、工序、设计版本和工程处置 |
| 数据泄漏导致虚高 accuracy | 高 | 相邻帧或同一视频跨 split | 按 lineage 传递闭包分组，QA 独立复查 |
| 前端把原型页面当真实系统 | 高 | mock 指标与真实统计无区分 | 页面级状态标识，正式演示只走真实主流程 |
| 把本地哈希/签名称为区块链 | 高 | 材料出现链上、公证、绝对不可篡改 | 统一改为“本地篡改可检测”；没有第三方回执不升级措辞 |
| 基础设施过度建设 | 中高 | 真实 baseline 未完成就做多副本/复杂 GIS | 以 Gate B 为进入条件 |
| 材料与系统版本不一致 | 高 | 冻结后仍手填截图和数值 | 自动导出事实，材料标注 build/model/data/run ID |

## 10. 答辩表述红线

在取得相应证据前，禁止使用以下表述：

- “识别准确率已达到 85%”或“影像分析准确率达到 90%”；
- “正式盲测通过”“评测环境完全隔离”；
- “区块链存证”“司法存证”“可信时间戳”“绝对不可篡改”；
- “自动 QGIS/CAD 空间配准”；
- “实时施工进度跟踪”，除非已定义事件、延迟、硬件和测试方法；
- “多源融合已在真实现场验证”，除非有第二来源及融合影响证据；
- “模型已用于真实施工生产”或任何未获得企业/现场证明的产业效果；
- 原 Demo 中无支撑的 `90%+`、`3.2s`、`98%`、`60%+`、`100% 可信`。

推荐的当前诚实表述是：系统已实现可运行的工程闭环和本地篡改检测；真实算法、授权数据和正式指标评测正在第二阶段建设，演示夹具与非正式证据均有显式标识。

## 11. 下一次评审需要的最小输入

下一次项目评审不需要更多概念图，首先需要以下五项事实：

1. 报名审核状态截图和版本化团队名单；
2. 项目统筹、算法/数据、QA、材料、赛事联络人的书面确认；
3. 唯一算法主线 ADR；
4. 数据来源、许可、标签和切分 manifest；
5. 第一个真实非 mock baseline 的可重复运行记录。

缺少其中任一项时，项目仍可继续改善软件体验，但不能把第二阶段判定为“真实算法与指标阶段已经完成”。
