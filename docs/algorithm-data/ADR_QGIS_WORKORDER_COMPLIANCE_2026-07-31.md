# ADR：产品主线冻结为 QGIS 工单式施工合规验真

ADR 状态：`accepted`（工程主线）  
提出/冻结日期：2026-07-31  
决策范围：产品与后端领域主线；**不等于**正式算法指标路线已选定或 90% 已达标

## 1. 决策

将系统收口为：

> **QGIS/GeoPackage 工程对象驱动的工单式施工合规验真系统**

核心闭环：

```text
授权且脱敏的 GPKG/QGIS 设计数据
  → 导入工程对象、版本和设计要求
  → 生成施工工单
  → 工人从指定工单拍照上传证据
  → 绑定 task_id、采集时间、GPS、GPS 精度
  → AI 仅输出可观察字段
  → 后台规则引擎与设计要求比对
  → 人工复核、整改、复验
  → 报告、证据包、完整性核验
```

明确 **不做**（P0 通过前禁止扩张）：CAD 全量解析、3D 数字孪生、RTSP/WebRTC 直播、真实 IoT 硬件平台、区块链/司法存证宣传、通用大屏美化、仅安全帽识别的通用安防网站。

## 3. 架构原则（不可突破）

1. **AI 只输出观察结果，不裁定是否合规。** 合规由后端规则引擎根据冻结的设计快照计算：`expected / observed / difference / verdict`。
2. **工单 ID 是主关联，GPS 是二次校验。** 不得仅靠“距离最近的管线”猜测归属。
3. **坐标系严肃处理。** 导入时保存 CRS；距离计算前统一 CRS；禁止投影坐标与经纬度混算。
4. **深度不可由普通单张照片虚构。** 无标定/尺度/深度设备时返回 `insufficient_evidence` / `manual_measurement_required`。
5. **指标评测与业务运行严格分离。** demo/fixture/合成 GPS 永久标记。

## 4. 「官方澄清」证据状态

用户提供的实现指令中涉及的「官方澄清」若仅以二次截图/转发文本出现：

- 状态：**待归档**，不是官方硬证据；
- 不得据此宣称组委会已书面确认 85%/90% 样本单元或「或」的最低合规解释；
- 正式口径仍以 `docs/source-reviews/COMPETITION_REQUIREMENTS.md` 及组委会书面答复为准。

## 5. 首个垂直切片（P0）验收

1. 导入脱敏/合成设计包（JSON 派生样例；真实 GPKG 仅受控存储）；
2. 创建 EngineeringObject 与 WorkOrder（如 PIPE-101）；
3. 从工单上传证据 + GPS，记录空间校验；
4. analyzer 输出观察字段；规则引擎输出合规/偏差/证据不足；
5. 进入既有人工复核、报告、证据包与完整性核验；
6. 全部 demo/synthetic 显著标识。

## 6. 后果

- 现有项目/基线/任务/复核/证据包链路 **复用，不重写**；
- `/gis-map` mock 必须逐步替换为真实 API（本轮可先提供后端 API + 联调入口）；
- 不得将 `DesignBaseline.expected` 的通用 JSON 继续当作唯一长期模型；工单冻结快照为合规权威。
